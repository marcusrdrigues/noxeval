# noxeval 0.4: repeat each case to tell variance from regressions

Status: approved by Marcus (2026-10-03), implemented the same day. Additive: without `repeat`, a run behaves exactly like 0.3.

## Why

A model is not deterministic, so one run says "passed" or "failed" while the truth is a rate. In the Nox battery, the same case on the same prompt passed in one run and failed in the next (`agente-case`, an answer over the length limit), and a privacy case failed once in four runs on an unchanged prompt. With one attempt per case you can't tell a regression from a bad draw, and a fix can look like it worked when it only got lucky.

Asking each case N times turns "pass/fail" into "passes 4 of 5", which is what a decision needs.

## The rule: safety has zero tolerance, quality has a threshold

This follows the line noxeval already draws with `failureKind`:

- **Any safety failure in any attempt fails the case.** A leak, a foreign link, a missing refusal, a forbidden tool or a runaway loop that happens 1 time in 5 is a real problem, not noise.
- **Usefulness failures are compared with a pass rate.** The case passes when at least `minPassRate` of the attempts pass (default `1`, so every attempt must pass unless you lower it). A team can set `0.8` for style rules such as length while keeping zero tolerance for safety.

_Discarded:_ pass@k (passes if any of k attempts passes). It fits code generation, where you can try k times and keep the best; a user of a chat app sees one answer, so the useful numbers are the rate and "all k passed".

## Format and API

- Config `repeat: number` (default 1) and CLI `--repeat N`; `RunOptions.repeat`.
- Case field `minPassRate?: number` (0 to 1) overrides the run's `minPassRate` (config, default 1).
- `CaseResult` keeps the first attempt's answer, context, tool calls and judge verdict in the existing fields, so the blind review works unchanged. `passed` and `failures` cover all attempts (a case that leaked in attempt 3 must read as failed, with the leak listed), and `firstPassed` keeps the first attempt's verdict, which the judge agreement and the review compare against. (Changed during implementation; the draft kept `passed` and `failures` from the first attempt, which made a failed case look green.) It adds, when `repeat > 1`:
  - `attempts: { passed, failures, ms, answer, toolCalls? }[]`;
  - `passRate` (passed / N) and `passRateLow`, the lower bound of the 95% Wilson interval. With 5 attempts, 5 of 5 only says the true rate is likely above about 57%; the bound keeps a small N honest.
- Report: `repeat`, and `flaky`: ids of cases that passed some attempts and failed others.
- Markdown: a "Flaky cases" table (id, rate, the failures seen). Terminal: the case line shows `4/5` next to the mark.
- Pure helpers exported for apps with their own runner (Nox has one): `summarizeAttempts(attempts, minPassRate)` and `wilsonLow(passed, total)`.

## Costs, stated up front

- N times the calls to the app, and N times the time unless `concurrency` is raised. `run` prints the number of calls before starting when `repeat > 1`.
- **The judge grades the first attempt only.** Judging every attempt multiplies judge cost by N for little gain: the judge is there to check the checks, not to measure variance.
- **The blind review stays one answer per case** (the first attempt), for the same reason: ten minutes of human grading, not fifty.

## Out of scope

- Statistical tests between two runs ("did the fix change the rate?"). The rate and its lower bound in each report are enough to compare by eye at these sizes.
- Seeds or temperature control. noxeval treats the app as a black box; if the app exposes a seed, the target can send it.

## Nox (site) adoption, after release

- `scripts/nox-eval.mjs` gains `--repeat N`, using `summarizeAttempts` with the same rule: safety zero tolerance, `minPassRate` 0.8 on the length-sensitive agent case.
- `/nox` shows the rate on cases run with repeats, and the history records `repeat`.
