# noxeval 0.6: a regression gate for RAG apps

Status: scope approved by Marcus (2026-10-10), implemented the same day in four pull requests (#3 citations, #4 baseline, #5 recorded answers, #6 cost and latency) and released as 0.6.0. Additive: without the new config keys, a run behaves exactly like 0.5.

## Why

noxeval answers "does every case pass?". A team that changes a prompt, a model or a retrieval step every week needs a different question answered: **"did anything get worse than the last run we accepted?"** Without it, a suite with one known-flaky case fails every run, people learn to ignore the red, and a real regression slips through.

This spec comes from adopting noxeval as the regression suite of a second app: a legal RAG assistant written in Java, where every answer must cite the passages it received by id (`[cdc-art-6]`), refuse when the passages don't answer, and stay within a cost per answer. Four things were missing, and each one is useful to any RAG app:

| #   | Feature                   | What it answers                                                                 |
| --- | ------------------------- | ------------------------------------------------------------------------------- |
| a   | Citations by id           | Did the answer cite only sources it received, and the ones it had to?           |
| b   | Baseline and regression   | What got worse, what got better, what is flaky, compared with the accepted run? |
| c   | Recorded answers target   | Can an app in Java, Python or anything else be graded without an HTTP endpoint? |
| d   | Cost and latency per case | Did a change make the app slower or more expensive beyond a limit?              |

Recommended order: a, b, c, d. Each can ship alone.

## a. Citations by id

0.5 left per-sentence citation checks out of scope because "they need the app to number its sources". This keeps noxeval black-box: the app reports **which sources it gave the model, with their ids**, and noxeval reads the ids the answer cites with a pattern. No change to how the app works.

- `TargetResponse.sources?: { id: string; text: string }[]`. When present, `context` defaults to the sources' texts, so grounding (0.5) and the judge keep working unchanged. `httpTarget({ sourcesPath })` reads it; `functionTarget` returns it.
- Config `citations?: { pattern?: string }`: the regex that finds a cited id in the answer. Default `\[([A-Za-z0-9][\w.:/-]*)\]`, which matches `[cdc-art-6]` and `[3]` alike.
- Case fields:
  - `mustCite?: string[][]`: groups, like `mustInclude`; each group needs one of its ids cited (`[["cdc-art-6"], ["sumula-stj-297", "sumula-stj-302"]]`).
  - `mustNotCite?: string[]`: ids that must never be cited (a planted poisoned passage, for example).
  - `citations?: false`: skip the check (refusals cite nothing).
- Failure codes:
  - `citation-unknown`: cites an id that was not among the sources. **Safety failure**: it is an invented source.
  - `citation-forbidden`: cites an id from `mustNotCite`. **Safety failure.**
  - `citation-missing`: a `mustCite` group was not cited. Usefulness failure.
- A case with `mustCite` whose target reports no `sources` fails with `no-sources`, never passes unverified (same rule as `no-trajectory` in 0.3).

## b. Baseline and regression

- `noxeval run --baseline <file>` (or `baseline` in the config) compares the new report with a previous one, case by case:
  - **regressed:** passed in the baseline, fails now; or any new safety failure;
  - **fixed:** failed in the baseline, passes now;
  - **flaky:** with `repeat > 1`, passed in some attempts (0.4);
  - **new** and **removed** cases.
- **Exit code with a baseline:** 1 only when something regressed. A case that already failed in the baseline does not fail the run again, but it stays listed, so known failures are visible and never silent.
- `noxeval baseline update [--from <report>]` writes the baseline from a report. **Never automatic**: accepting a new baseline is a reviewed change, committed with the change that caused it.
- The baseline file is a trimmed report (ids, verdicts, failure codes, pass rates, cost and latency), small enough to commit. Answers are not stored in it.
- Markdown summary: a "Compared with the baseline" table first (regressed, fixed, flaky, unchanged), then the usual report.

## c. Recorded answers target

- `jsonlTarget(path, { idField = "id" })`: reads one JSON object per line, `{ id, answer, context?, sources?, toolCalls?, meta?, costUsd?, ms? }`, and answers each case from the line with its id. A case with no line fails with `no-answer`.
- Why: the app generates the answers with its own code path (its prompts, adapters and caches) and noxeval grades the file. The app can be written in any language and needs no test endpoint. With `repeat`, the file may hold several lines per id, used in order.

## d. Cost and latency per case

- `TargetResponse.costUsd?: number`. `ms` is already measured by noxeval; a target may override it with its own `ms` (time inside the app, without the network).
- Case and config fields `maxCostUsd?` and `maxLatencyMs?`, failing with `over-cost` and `over-latency` (usefulness failures).
- Report: total and p90 cost, p95 latency; with a baseline, the change in percent. A rise above `costWarnPercent` (default 20) is a warning, not a failure.

## Programmatic API

Exported and pure: `checkCitations(answer, sources, case, { pattern })`, `compareReports(baseline, current)` and `toBaseline(report)`. `jsonlTarget` lives in `adapters`.

## Out of scope

- Checking that the cited passage **supports** the sentence (meaning). That stays with the judge; the deterministic part is the id.
- Storing the baseline anywhere but a file the team commits.
- Exporting the run as OpenTelemetry traces: a later version.

## Acceptance

1. An answer citing `[x]` when the sources were `[a, b]` fails with `citation-unknown`, a safety failure, even with `repeat` and `minPassRate < 1`.
2. `mustCite: [["a"], ["b", "c"]]` passes with `[a]` and `[c]`, fails with only `[a]`.
3. A case with `mustCite` and no `sources` fails with `no-sources`.
4. With a baseline where case X failed and still fails, and nothing else changed, the run exits 0 and lists X as a known failure.
5. A case that passed in the baseline and fails now makes the run exit 1, and the Markdown summary lists it under "regressed".
6. `baseline update` is the only way the baseline file changes.
7. `jsonlTarget` grades a file of recorded answers with no network call; a missing id fails with `no-answer`.
8. `maxCostUsd` fails a case whose `costUsd` is above it; without `costUsd` the check reports "not checked".
9. No new runtime dependency.

## Changed during implementation

Decisions the spec left open, settled before each pull request:

- **Citations.** The settings live in `checks.citations`, next to `grounding`. The default pattern skips Markdown links (`[here](https://...)`): read as a citation, every link would be an invented source, a safety failure. `mustNotCite` is checked even without sources, since it needs only the answer, and a forbidden id is reported once, as forbidden. A malformed item at `sourcesPath` throws instead of being dropped.
- **Baseline.** A new case that fails is a regression: nobody accepted that failure. A known failure regresses when it gains a safety failure **code** it didn't have; the same code with another detail does not. The file keeps failure codes, not details, and no per-case latency, so an update is a small diff. A missing baseline file means "every case must pass" (stricter, never looser). `baseline update` refuses a partial run and never overwrites a file that is not a baseline, and baseline paths must be inside the project folder (a SonarCloud finding: a misled agent passing `--baseline ~/.bashrc`). A fixed case gets a note to accept it, since until then it is not guarded.
- **Recorded answers.** Targets got an optional `prepare(suite)` hook, so a broken file stops the run before any case with every problem listed, and ids that match no case become report notes. `TargetResponse.ms` came with this item, not with d: reading a file takes 0 ms, and a line without `ms` is "not measured" instead of a false 0 ms latency. With `repeat`, lines are never reused.
- **Cost and latency.** `httpTarget` reads `costPath` and `msPath`. The cost warning against the baseline compares the cost **per answer** (mean and p90), not the total: adding cases raises the total without anything getting more expensive. The total sums every attempt, since it is what the run spent. Latency changes are shown without a warning setting.
